# Translation units of the game code, 0x760000..0x948000

Which source file each function of the ported PS2 game code came from. This is Project Zanarkand
PROGRESS item 1.1.7. The table at the end is generated by `tools/tu_map.py` and covers every one of
the 9,923 functions in the range, each one either in a translation unit or marked unattributable
with the reason.

## The short version

- **9,923 functions, 374 rows.** 797 functions (8.0%) sit in 36 named source files, 8,493 (85.6%)
  in 250 unnamed units, and 633 (6.4%) are unattributable. So 93.6% of the range has a unit.
- **The named files are solid. The unnamed units are lower bounds.** A named file has a `__FILE__`
  path string read inside it, or a range another doc proved function by function. An unnamed unit is
  a run with data-order evidence at its edges and nothing that names it. Calibrated blind against
  Lua and the rc libraries, the rules find about 70% of real file boundaries and add about one false
  boundary per real one. So a small unit is usually a whole file or half of one. The 14 units over
  150 functions (4,103 functions) have no boundary evidence inside and are probably several files
  each.
- **The method is the layout law seen from the data side.** Objects are laid out in link order in
  every section at once, so `.rdata`, `.data` and `.bss` all rise with code address one object at a
  time. Inside an object the code is alphabetical and the data is in source order, so the data of
  neighbouring functions interleaves. An interleave across a cut means the cut is inside one object.
  A clean cut with enough data on both sides is an object boundary.
- **77 library names in the range are wrong.** FLIRT matched tiny game stubs to CRT and STL
  signatures (`__cfltcvt_init_80 0x777940` writes the `"ffxpassf"` strings, `__getmbcp 0x863220`
  reads `g_ffxAlBhedPrimerGrantArmed`). They are game functions in game files. List in section 7.
- **No `<Module>__f<ADDR>` name is wrong.** The 30 still in the range all sit in the row of their
  own file. The README's 199 is stale, see section 7.
- **The IDB comment applier rehearsed clean** on a copy: 341 to add, 341 written, 0 on the second
  dry run. It is `tools/apply_tu_comments.py`, see section 8.

## 1. The layout law, and why the data side works

`LUA_MODULE.md` found that MSVC lays out each object file's functions alphabetically by symbol
name, and that the object files follow link order (the Lua files are not alphabetical by file
name). That law maps a known library onto addresses when a symbol list exists. The game code has
no symbol list, so the law has to be used the other way round: to find where one object ends.

Every section follows the same object order. So if object A is linked before object B, all of A's
code is below B's code, all of A's `.rdata` is below B's `.rdata`, and the same for initialized
`.data` and for `.bss`. Measured over the range, in 0x8000-byte code buckets of first-user items,
the median data address climbs steadily in all three [V, measured]: `.rdata` from 0xB51980 at code
0x760000 to 0xB68D94 at 0x938000, `.data` from 0xC3E720 to 0xC61090, `.bss` from 0x10D55CC to
0x193C360. The few dips are buckets whose median lands on a shared item or a COMMON symbol
(section 6), which the trend filter below removes.

Inside one object the two orders disagree. The code is alphabetical. The string literals and
statics are in source order, or something close to it. So the data addresses of neighbouring
functions in one object interleave, and at a real object boundary they cannot.

The cleanest example in the game code is the effect API at 0x7FCA90..0x7FCDD0 [V]. Each function
prints its own name, and the code runs `op_et_weapon_free` 0x7FCA90, `op_event_effect_free`
0x7FCBF0, `op_event_effect_init` 0x7FCC20, `op_fp_effect_free` 0x7FCC40, `op_fp_effect_init`
0x7FCC60, `op_ovl_effect_free` 0x7FCD60, `op_ovl_effect_init` 0x7FCDD0. That is ASCII order.
Their strings run the other way, 0xB58520 for `op_event_effect_free` down to 0xB58490 for
`op_ovl_effect_init`. The functions are sorted and their data is not.

chr.c gives a second check. Its functions log their own PS2 names, `"SG:Ch_Allocate"` at 0x824F90,
`"SG:Ch_BlkAllocate"` at 0x825760, `"SG:Ch_Dispose"` at 0x8266F0 [V], and those three are in ASCII
order. The first function of chr.c, 0x824F00, logs both `"SG:ChN_DataDispose"` and
`"SG:Ch_DataDispose:%s"`. If it is `ChN_DataDispose` it sorts first, because `N` (0x4E) is below
`_` (0x5F) [I].

## 2. What counts as evidence

**Which data points are trusted.** A `.rdata` item belongs to its first user in code order,
because a pooled literal is kept in the first object that has it (MSVC `/GF`). A `.data` or `.bss`
item counts when it has one user function, or a few users within 0x800 bytes of code. An item
without a name is skipped, because that is a reference into the middle of something. Then a trend
filter: the longest non-decreasing run of points is the backbone, and a point more than 0x800
(`.rdata`), 0x1000 (`.data`) or 0x20000 (`.bss`) bytes off the backbone near its code address is
dropped. Over the whole analysis window (0x740000..0x968400) that removes 1,406 points, mostly the
C tentative definitions (section 6), the float constant pool around 0xB92000 and the EH tables
around 0xBFC000. What is left is 4,138 `.rdata`, 591 `.data` and 3,695 `.bss` points, and 1,998
functions of the range own at least one of them. The other 7,925 own no trusted data.

**The cut test.** For a cut between two functions, look at the points of the 120 functions on each
side. In each section, count the fewest points that have to be thrown away so that everything left
of the cut sits below everything right of it. Sum over the sections. A score above 1 is an
interleave and the two sides are joined. One stray point is forgiven, because one shared or
misattributed item is common. Joined runs form groups, and every group with data is a piece of one
object [V for the interleave, it is read straight off the operands].

**How strong a clean cut is.** Two neighbouring groups with k1 and k2 data-owning functions, both
from one object whose code and data orders are unrelated, come out cleanly ordered with chance
about 1/C(k1+k2, k1). So:

| left edge in the table | rule | meaning |
|---|---|---|
| `doc` | a range from `RCBG.md`, `RCDATA.md` or `RCFLEX.md` | proved there function by function [V], or [I] where that doc says so |
| `anchor` | two different file anchors with no other boundary between them | there must be one here, placed at the best clean cut between them [V that it exists, I where] |
| `data k1/k2 C=` | k1 and k2 at least 2, C at least 10 | a chance one below 10% [V, statistical] |
| `data-weak` | k1 and k2 at least 2, C 6 to 9 | one in 6 to one in 9 [I] |
| `clean k1/k2` | any other clean cut | stands unless an anchor or an edge ties the sides [I] |
| `name A/B` | inside a data-less run of 12 or more, three behaviour names of one family then three of another with no mixing | only as good as the names earlier passes gave [I] |

A clean cut is not a boundary when the same file anchor is on both sides (contiguity) or when any
call, shared item or adjacent table slot links the two sides (the tie). Two clean cuts were refused
that way inside files other docs had already proved, `rcbgFP.c` (0x9225D0 to 0x922600) and
`rcbgLoadText.c` (0x93A280 to 0x93A650). That shows why a 1/1 cut alone is weak.

**Placing a boundary inside a data-less gap.** Most gaps between two groups hold functions with no
data at all. The boundary goes where the fewest call, shared-data and table edges cross it, counted
against 60 functions of context on each side, after two rounds of propagation through edges inside
the gap. When several positions cost the same, the functions between them are listed as
**unattributable**, with the two neighbours as the only candidates. That is 85 runs and 630
functions. Three more functions own nothing and have no anchor and no name, so nothing places them.

**Anchors.**

- A `__FILE__` path string read inside a function names that function's file [V]. Outside the rc
  libraries, 11 files have a reader in the range. The 25 single rc files and 8 multi-file rc rows of
  `RCBG.md`, `RCDATA.md` and `RCFLEX.md` are in `CURATED` in the tool, with their source doc.
- A surviving `<Module>__f<ADDR>` name ties its function to the file whose path string has the same
  base name [V, the name came from that string].
- A file name inside a Virtuos comment only ties neighbours and does not name the unit: `btllimitwk.c`
  in `MsSetReel 0x7B1B50` (the comment says `MsSetReelResult` comes from that file, and the function
  only calls it), `math.c` in `op_m_normalize 0x7E8030`, `op_mul_m33 0x7E8B00`, `op_vector_m
  0x7EA760`, and `u_15.c` in `opu_part_run 0x80B800`. These show as notes in the evidence column.
- A module name with no path string behind it (`VfxPm`, from the yonishi pass) is only a note too.
- A named file's **core** is the span from its first to its last anchor function, widened to the
  interleave groups that hold them. Inside the core the file is proved [V]. Between the core and
  the row edge it is only "no boundary found" [I].

## 3. Calibration

The rules were tested blind (`--no-curated`, and `--range 94A3D0 968390` for Lua, which is outside
the report range) against two sets where the true file boundaries are known.

| set | true boundaries | found exactly | inside an unattributable run | false boundaries |
|---|---|---|---|---|
| Lua 5.2, 30 files, `LUA_MODULE.md` | 29 | 15 | 5 | 22 |
| rc libraries, 24 single files, `RCBG.md`, `RCDATA.md`, `RCFLEX.md` | 26 | 18 | 1 | 20 splits inside the single files |

Lua is the harder case. lapi.c's 83 API functions reference no data at all. The thresholds in the
tool (one forgiven point, a tie on any shared edge, clean cuts with one data function) were the
best found on both sets together. Raising the clean-cut minimum lost real boundaries faster than
it removed false ones. A modularity segmentation of the call graph was tried and dropped, because it
gave 23 to 36 false splits in the rc set whatever its resolution.

So read an unnamed unit as "one object, or a part of one", and a unit over about 150 functions as
"several objects with no evidence between them".

## 4. Strongest anchors and weakest calls

The five strongest:

1. **chr.c.** `push offset "..\proj\src\chr\chr.c"` twice in `FFX_Ch_MoveChrMemory` (0x826FC4 and
   0x8271AC) [V]. Its start is a strong data boundary at 0x824F00, groups of 8 and 25 with
   C=13,884,156 [V]. Its own SG log names run in ASCII order (section 1). Core 0x824F00..0x829CE0.
2. **tklib.c.** 26 references to `"..\ps2lib\common\tklib.c"` across 0x88D520..0x88E6B0 and 7
   `tklib__f` names [V]. Core 0x88C860..0x88E928.
3. **libmscd.c.** 11 references to `"..\program\lib\src\libmscd.c"` across 0x76B920..0x76E660 and 5
   `libmscd__f` names [V]. Core 0x76B920..0x76E77A.
4. **The rc libraries.** Path strings plus every function placed by name in `RCBG.md`, `RCDATA.md`
   and `RCFLEX.md`. The exact name `rcbgPSimAddGravity 0x91F7C0` survives where the law puts it [V].
5. **movie_str.c and mem.c.** movie_str.c has 8 path readers 0x77BA70..0x77DF90 and 5
   `movie_str__f` names [V]. mem.c has its path string in 0x83C0F0 and a strong right edge at
   0x83C6F0 (17/2, C=171) [V].

The five weakest:

1. **The big units.** `unit_85E620` is 677 functions, the ATEL VM, 115 Core syscall handlers, save,
   field and premovie code, with no boundary evidence inside. It is certainly several files. 14
   units over 150 functions hold 4,103 functions [I].
2. **`clean 1/1` edges,** the most common left edge in the table. One function against one function
   comes out clean half the time by chance. Only the tie test filters them [I].
3. **File edges outside the core.** `movie_cd.c` runs 0x776F60..0x77760E but its only anchor is
   0x777080, so 0x776F60..0x77707F is movie_cd.c only because no boundary was found. 97 functions
   sit in this position, and the applier marks them `TU: name?` [I].
4. **The three name boundaries,** `FFX_Btl/FFX_BtlEv` at 0x7972E0 and `FFX_Yanagi/FFX_YanagiTask`
   at 0x92EC90 inside the Yanagi task engine. They rest on behaviour names earlier passes chose [I].
5. **Affinity placement.** Where a gap had any call or shared item, the boundary was put where the
   fewest edges cross it. A helper called from both sides lands on whichever side calls it more.
   The `RCBG.md` starts it marks [I] are inherited too: `rcbgPre.c` from 0x9215E0, where this IDB has
   no function (the first is `rcbgPreCreateDefaultSet 0x921640`), and `rcbgSave.c` from 0x938080.

## 5. Unattributable runs

Every unattributable row names the boundary it sits on. They come in two kinds.

- **Between two units (85 runs, 630 functions).** A boundary is known to be in the gap, and the
  functions in it have no edge that prefers either side. The largest: 0x806450..0x807820 (76,
  mostly tiny stubs, among them `unknown_libname_630..647` and the mangled STL names of section 7,
  none of which owns data), 0x855C70..0x856F19 (66) and 0x858250..0x859036 (60), both ATEL Core
  syscall handlers,
  0x7A3A80..0x7A4902 (43) and 0x7A4C70..0x7A577D (37), ATEL Btl syscall handlers. Syscall handlers
  are reached only through their library table and touch no data of their own, so neither side
  claims them.
- **No evidence at all (3 functions).** No data, no anchor, no behaviour name: 0x937F70, 0x9399F0
  and 0x93A270, small functions in the gaps between the `RCBG.md` file ranges.

## 6. Where the law breaks

- **Files are in link order, not alphabetical.** Known from Lua. The rc libraries confirm it:
  Guide, PSim, Scene, rcBBox, Pre, Main, TrxTex, FP, rcdtTm2, rcdtRsd2, ..., and the rcFlex files
  Particle, Spring, Nail, Damp, Gravity, Wind (`RCBG.md` 2) [V].
- **File-static helpers come first, in source order.** Each rcFlex file and rcbgPSim.c opens with
  its own copy of `VecAdd`, `VecScale`, `VecCopy`, `VecSub` in that order, then the public functions
  alphabetically (`RCFLEX.md` 1) [V]. The copies have equal lengths and different bytes, because
  each reaches its own object's constants [V, compared here].
- **Identical functions are not folded (no `/OPT:ICF`).** 40 groups of byte-identical functions of
  16 bytes or more survive in the range, 101 functions [V]. The clearest is the angle wrap helper,
  11 identical copies: 0x829800, 0x82BA70, 0x82DB50, 0x836720, 0x83A010, 0x845640, 0x84D330,
  0x84EB60, 0x853000, 0x854200 and 0xA7AE20. A header static is emitted once per object, so each
  copy marks its own object. The 8 copies the tool can see all landed in 8 different rows, an
  independent check on the map [V copies, I one per object]. The flip side is that identical bodies
  inside one file are common too (7 copies of `sub_8E9720` within 0x2500 bytes), so a duplicate is
  not a boundary by itself.
- **C tentative definitions are not in object order.** chr.c's own `.bss` is around
  0x12FBC60..0x12FBDA8, but `g_ffxChrCount 0x23C44E0` and `g_ffxChrArray 0x23C44E4` sit 0x10C0000
  bytes higher [V addresses]. A C global declared without an initializer and without `static` is a
  COMMON symbol, and the linker places those after all the `.bss` contributions [I]. The trend
  filter drops them, which is most of the 1,406 dropped points.
- **Pooled literals belong to their first user.** A string two files use lives in the earlier
  file's `.rdata`, which is why only the first user owns a `.rdata` point [I, standard `/GF`].
- **Lua is packed, the game code is aligned.** Lua has 81 function starts that are not 16-byte
  aligned, and none of its file boundaries is. In 0x760000..0x948000 only 5 of 9,923 starts are
  unaligned [V]: three 6-byte tails (0x76EBFE, 0x7A6DCA, 0x7A751F), `sub_89023A` (0xD8 bytes) and
  `__cfltcvt_init_103 0x909379` (0x2A bytes), all of which look like IDB fragments [I]. So padding
  carries no boundary signal in the game code, unlike Lua.
- **One behaviour family can span two objects.** `FFX_Mot` names run 0x833F50..0x839F50 in
  `MAP.md`, but there is a strong data boundary inside it, between `FFX_Mot_WrapAnglePi 0x836790` and
  `FFX_Mot_ReleaseAllNonSystemB 0x836A80` (27/21) [V]. The two angle wrap copies at 0x836720 and
  0x83A010 fall one on each side, which agrees.

## 8. TU comments in the IDB

`tools/apply_tu_comments.py` adds a repeatable function comment to the 36 named-file rows only. Inside
a proved core it writes `TU: chr.c (TRANSLATION_UNITS.md)`, and between the core and the row edge
`TU: chr.c? (TRANSLATION_UNITS.md)`. It only touches a function with no function comment at all,
repeatable or not, and never saves. Unnamed units are left out on purpose, because their edges move
whenever the rules change.

Rehearsed on a copy of the IDB with `--rehearse` (dry run, apply, dry run in one session): 341 to
add (244 in a core, 97 at an inferred edge), 341 written, 0 failed, then 0 left on the second dry
run. 456 functions in those rows already carry a comment and were skipped.

```
"<IDA>/venv/Scripts/python.exe" -I tools/apply_tu_comments.py --idb COPY.i64 [--apply] [--rehearse]
```

Inside IDA it runs with File > Script file, dry by default (`DRY_RUN = True`).

## 9. Rerunning

```
"<IDA>/venv/Scripts/python.exe" -I tools/tu_map.py dump --idb COPY.i64 --out tu.json
python -I tools/tu_map.py report --dump tu.json --doc reversing/TRANSLATION_UNITS.md [--tsv tu.tsv]
python -I tools/tu_map.py report --dump tu.json --no-curated --tsv blind.tsv
python -I tools/tu_map.py report --dump tu.json --range 94A3D0 968390 --tsv lua.tsv
```

The dump reads 11,540 functions from 0x740000..0x968400 (the range plus context, Lua included for
the blind test) in seconds and never saves. The report is plain Python. `--doc` rewrites only the
table between the markers below. The dump is deterministic: two dumps of the same copy compare
byte-identical. A unit is named `unit_<start>` after the first function of the whole unit, which can
lie below 0x760000 (`unit_75FDA0`). When the rules or the IDB change, ROWS in the applier should
be regenerated from `--tsv` (columns 1, 2, 4, 7 and 8 of the `file` rows).
